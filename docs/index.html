lsm-storage-engine

A single-node, log-structured merge-tree key-value store written from scratch in C++20 — a write-ahead log with crash recovery, immutable SSTables with a sparse index, per-table bloom filters, and size-tiered background compaction. The engine depends on the standard library only; CRC32 and the bloom hashing are hand-rolled.

What it is

An LSM-tree is the write-optimised structure behind RocksDB, Cassandra, and most modern storage layers: writes go to a log and an in-memory sorted structure, which is periodically frozen into an immutable sorted file, and those files are merged in the background. This is that design built end to end — not a wrapper, not a tutorial port.

It is not a RocksDB competitor. It is a from-scratch engine built to understand and defend every layer, measured honestly on stated hardware with the methodology written down.

1
Write-ahead log
Each mutation is appended as a CRC32-framed record and fsynced before the memtable is touched, so a crash never loses an acknowledged write. On open the log is replayed; a torn or corrupt tail record is detected by CRC and truncated.
2
Memtable — a hand-written skip list
Ordered, tombstone-aware, with memory accounting driving the flush threshold. Inserts touch only the search path, which is what makes single-writer / multi-reader access viable without locking readers out.
3
SSTable flush
Past its size threshold the memtable is written out as an immutable table: sorted data blocks, a sparse one-entry-per-block index, a bloom filter, and a fixed 40-byte footer. The manifest is then updated by atomic rename — the single durability point — and the log is rotated.
4
Reads
Memtable first, then tables newest to oldest, stopping at the first hit or tombstone. Each table's bloom filter lets a lookup skip a table that cannot hold the key, turning a miss from one block read per table into roughly fpr block reads.
5
Background compaction
One background thread k-way-merges similarly sized tables, dropping shadowed values and safe tombstones. Readers take a reference-counted immutable snapshot of the table set, so compaction never blocks or breaks an in-flight read — verified under ThreadSanitizer.

Benchmarks

How these were measured
  • Machine: Intel Xeon @ 2.80 GHz, 4 vCPU, 16 GB RAM, Ubuntu 24.04, ext4 — a KVM guest, not bare metal.
  • Method: 50,000 operations per workload, 100,000-key set, 16-byte keys, 100-byte values, 4 MiB flush threshold, seed 42. Every workload runs 3 trials and the median is reported; the bars below span min to max so run-to-run noise is visible.
  • Reads are CPU-bound, not disk-bound. The working set is about 12 MB on a 16 GB machine, so after the warm-up pass it is entirely in page cache. These numbers measure the lookup path — bloom probe, index binary search, block parse, one pread — not the storage device.
  • Writes are fsync-bound, so their throughput is a property of the host's storage, not of the engine. On a different VM instance the same binary measured 1,556 ops/s with a 595 µs p50; here it is 5,311 ops/s at 176 µs. In both cases p50 ≈ one fsync — that invariant is the real result, not the absolute number.
  • Single-threaded client; each operation timed individually with steady_clock. Raw JSON is committed in the repo.

Two tail effects are visible and both are explained rather than hidden. Reads sit at 2.5 µs through p99 but jump to ~30 µs at p99.9 — background compaction and scheduler preemption on a 4-vCPU guest. And the worst single write in a fill run is ~34 ms: that is a memtable flush running synchronously under the write lock, which is exactly the limitation named below. An async flush is the fix, and the benchmark is what makes the cost concrete.

Zipfian reads beat uniform reads (852k vs 763k) because a skewed key distribution keeps the hot blocks and skip-list nodes in cache — the result you'd expect if the benchmark is measuring something real.

The profiling win

Profiling the read path with callgrind found one dominant hotspot: SSTableReader::Get allocated a fresh block buffer per lookup, and resize() zero-filled about 4 KiB that pread then immediately overwrote. Nearly half of all read-loop instructions were spent on a memset whose result was thrown away.

The fix was a reused thread_local block buffer plus a PreadInto that skips the zero-fill.

The two genuine-work entries are identical in absolute terms before and after. Only the overhead disappeared, which is what a real optimisation looks like as opposed to a benchmark that quietly stopped doing the work.

What it bought in wall-clock time

On the same machine, five trials each: 620,018 → 710,090 ops/s median (+14.5%), p50 1.35 µs → 1.14 µs. The trial ranges do overlap — 574.7k–713.6k before against 634.4k–802.3k after — so the honest reading is that wall-clock gain is real but noisy on a shared vCPU, and the instruction count is the measurement worth quoting.

How it is built and checked

Warnings are errors
Built with -Wall -Wextra -Werror on both gcc and clang, in Debug and Release. clang-tidy and clang-format run in CI on every push.
Every test under sanitizers
74 tests run under AddressSanitizer and UndefinedBehaviorSanitizer, and — once the compaction thread existed — under ThreadSanitizer, which is what backs the lock-free-read claim rather than an argument that it looks right.
Crash recovery is tested, not asserted
Recovery tests truncate and corrupt the log at record boundaries and in the middle of records, then assert that every acknowledged write survives and the bad tail is dropped.
Standard library only
No third-party code in the engine. CRC32 and the bloom filter's double hashing are implemented from scratch; GoogleTest and a matplotlib plotting script are the only outside dependencies, and neither ships in the engine.

Design decisions

A Status type, not exceptions
A storage engine's failures — a short read, a bad CRC — are expected control flow, not exceptional. One uniform Status across the API keeps every failure path visible at the call site.
A skip list, not a balanced tree
No rotations to get right, and an insert touches only the search path — the property that makes lock-free single-writer / multi-reader access possible, and the reason it is the industry default here.
Atomic manifest via write-temp + rename
rename is atomic on POSIX, so a torn manifest is unrepresentable and needs no checksum. The manifest commit is the single durability point for a flush or a compaction.
Immutable snapshot reads, not a shared_mutex
A read copies a reference-counted snapshot pointer under a brief lock, then reads with no lock held. A concurrent compaction can swap in a new table set and even delete the old files without breaking an in-flight read, because POSIX keeps the inode alive behind the open descriptor. Under a shared_mutex readers would hold a lock across their I/O.
Size-tiered compaction, not leveled
Lower write amplification and far simpler to implement correctly; it accepts higher transient space amplification, which is the right trade at single-node scope. Leveled is the answer when disk is the binding constraint.
fsync on every write
The strongest and simplest durability guarantee. The cost is throughput, which the benchmark quantifies rather than hides — and group commit is the known remedy.

Limitations

Stated plainly, because a storage engine with no listed limitations is one that has not been measured.

  • Single node — no replication, sharding, or distribution.
  • Single writer — writes serialize under a mutex; reads are concurrent.
  • Point lookups only — no range scans or user-facing iterators yet.
  • No transactions, MVCC, or snapshot reads.
  • No compression, and size-tiered compaction only.
  • Synchronous flush — a flush runs under the write lock, which is the ~34 ms worst-case write visible in the table above.
  • Orphaned SSTables leak — a table written by a flush or compaction that crashed before its manifest commit is correctly ignored on restart, but never deleted.

What I would build next

  • Group commit — batch many writers' records into one write + fsync. This is the measured write bottleneck, so it is first.
  • Range scans — the per-table ordered iterator already exists for compaction; this is a k-way merge with tombstone shadowing exposed as API.
  • Leveled compaction — trade write amplification for much lower space amplification.
  • Async flush — freeze the full memtable and flush it off the write lock, removing the tail stall above.
  • Snapshot reads / MVCC — tag keys with a sequence number, formalising the internal immutable snapshot into a user-visible one.
