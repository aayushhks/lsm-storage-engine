lsm-storage-engine

A single-node key-value store written from scratch in C++20. It has a write-ahead log with crash recovery, immutable SSTables with a sparse index and bloom filters, and size-tiered background compaction. The engine uses only the standard library.

How it works

1
Write-ahead log
Every write is appended to a CRC32 framed log and fsynced before the memtable changes, so a crash never loses an acknowledged write. On open the log is replayed, and a corrupt tail record is detected and dropped.
2
Memtable
A hand-written skip list holds recent writes in sorted order and tracks its own memory use to decide when to flush.
3
Flush to an SSTable
A full memtable is written out as an immutable file: sorted data blocks, a sparse index, a bloom filter and a fixed footer. The manifest is then updated by atomic rename, which is the point where the flush becomes durable.
4
Reads
Check the memtable first, then each table from newest to oldest, stopping at the first hit. Each table's bloom filter lets a lookup skip a table that cannot hold the key.
5
Compaction
A background thread merges similarly sized tables and drops shadowed values. Readers work from an immutable snapshot of the table set, so compaction never blocks a read. This is verified under ThreadSanitizer.

Benchmarks

  • Intel Xeon 2.80 GHz, 4 vCPU, 16 GB RAM, ext4. This is a virtual machine, not bare metal.
  • 50,000 operations per workload, 100,000 keys, 3 trials with the median reported.
  • Reads are CPU bound here. The working set is about 12 MB on a 16 GB machine, so it sits in page cache and these numbers measure the lookup path rather than the disk.
  • Writes are fsync bound, so their speed depends on the host's disk. On a different machine the same binary did 1,556 writes/sec instead of 5,311. In both cases p50 is roughly one fsync.

The tail is where the honest answers live. Reads stay at 2.5 µs through p99 but reach about 30 µs at p99.9, which is background compaction and scheduler preemption on a shared vCPU. The worst single write in a fill run is about 34 ms, because a memtable flush runs under the write lock. That is a real limitation, listed below, and the benchmark puts a number on it.

The profiling win

Callgrind showed one dominant hotspot in the read path. SSTableReader::Get allocated a fresh block buffer on every lookup, and resize() zero filled about 4 KiB that pread then overwrote immediately. Almost half the read loop was a memset whose result was thrown away.

The fix was a reused thread_local buffer plus a PreadInto that skips the zero fill.

Design decisions

A Status type instead of exceptions
A short read or a bad checksum is expected control flow in a storage engine, not an exceptional event. One Status type across the API keeps every failure visible at the call site.
A skip list instead of a balanced tree
There are no rotations to get right, and an insert only touches the search path. That is what makes one writer and many readers workable without locking readers out.
Atomic manifest by rename
Rename is atomic on POSIX, so a half-written manifest cannot exist and needs no checksum. That single rename is the durability point for a flush or a compaction.
Snapshot reads instead of a shared mutex
A read copies a reference counted snapshot under a brief lock, then runs with no lock held. Compaction can swap in a new table set and delete the old files without breaking a read in flight, because the open descriptor keeps the inode alive.
Size-tiered compaction instead of leveled
Lower write amplification and much simpler to get right. It costs more temporary disk space, which is the right trade at this scale.
fsync on every write
The simplest strong durability guarantee. It costs throughput, which the benchmark measures rather than hides, and group commit is the known fix.

Limitations

  • Single node, and a single writer. Reads run concurrently.
  • Point lookups only. No range scans yet.
  • No transactions, MVCC or snapshot reads.
  • No compression, and size-tiered compaction only.
  • Flush runs under the write lock, which causes the 34 ms worst case above.
  • A table left behind by a crashed flush is ignored on restart but never deleted.

What I would build next

  • Group commit, batching many writers into one fsync. This is the measured bottleneck, so it comes first.
  • Range scans. The per-table iterator already exists for compaction.
  • Async flush, to remove the tail stall above.
  • Leveled compaction, trading write amplification for less disk use.
