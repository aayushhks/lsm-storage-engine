profiling pass

A 42% memset that pread threw away

Profiling the read path (callgrind — no perf in the CI container) found one dominant hotspot, and fixing it was a small, measurable win.

The finding

SSTableReader::Get allocated a fresh block buffer per lookup and resize() zero-filled ~4 KiB — bytes that the next pread immediately overwrote. Two of every five read-path instructions were spent on a memset that was thrown away, plus ~6% more in per-lookup malloc / free.

The fix

A reused thread_local block buffer (per-thread, so the concurrent read path stays race-free) and a PreadInto that skips the zero-fill. The buffer grows only when a larger block than any seen appears — after warmup, never.

design decisions

Every layer is a defended tradeoff

The full reasoning is in the design doc; each choice was made to be explained without notes.

Skip list over balanced tree

No rotations to get right, and inserts touch only the search path — the property that makes lock-free single-writer / multi-reader possible.

fsync-per-write over group commit

The strongest, simplest durability guarantee. The cost is write throughput, which the benchmark quantifies and group commit would recover.

Atomic manifest via write-temp + rename

rename is atomic on POSIX, so a torn manifest is unrepresentable — no checksum needed. The manifest commit is the single durability point.

Immutable snapshot over shared_mutex

Reads copy a reference-counted table-set pointer and run lock-free; a compaction can swap and delete files without ever breaking an in-flight read.

Size-tiered over leveled compaction

Lower write amplification and far simpler to implement correctly; it accepts higher transient space, the right call at single-node scope.

Bloom filter from scratch

Bit array + k probes via double hashing; a miss goes from one block read per table to ~fpr. FPR is a build parameter — measured 1.08% at the 1% target.

honest scope

Limitations

  • ·Single node, single writer — writes serialize under a mutex; reads are concurrent.
  • ·Point lookups only — no range scans yet.
  • ·No transactions, MVCC, or compression.
  • ·Synchronous flush — a large flush briefly stalls writers.
  • ·Orphaned SSTables leak after an interrupted compaction (ignored, not deleted).
understood, descoped

What I'd build next

  • →Group commit — batch many writers into one fsync; the measured write bottleneck.
  • →Range scans — a merge iterator across memtable + SSTables (the scan iterator already exists).
  • →Leveled compaction — trade write amplification for much lower space amplification.
  • →Snapshot reads / MVCC — sequence-numbered keys pinning a consistent version.
  • →Async flush — freeze the memtable and flush off-thread so writes never stall.
